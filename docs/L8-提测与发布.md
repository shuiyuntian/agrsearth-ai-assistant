# L8 提测与发布

> **测试底座自助发布**：团队用 `tools/publish.mjs` 自发布到 aiearth01 共享开发调试环境（需平台方开通
> 团队角色并下发凭据，见 `test-env/README.md`）。macOS/Ubuntu 经 `tools/publish.sh`、Windows 经
> `tools/publish.cmd` 调用同一 Node 实现，可自助迭代调试（含 `--dev-url` HMR 回路）。
> **生产发布权仍在平台方**：团队交付终点 = 提测单；平台方验收依据 =
> 平台仓 `docs/运维手册/2-部署与变更/PLUGIN_ACCEPTANCE.md`。

## 8.1 全流程

```text
团队                                                平台管理方
 │                                                     │
 ├─ 1. 本地开发、构建、接口测试                        │
 ├─ 2. 需要时接共享 Nacos + 前端 HMR 联调              │
 ├─ 3. 人工确认本地/联调证据                           │
 ├─ 4. 批准发布；后端 deploy=true 另需明确批准          │
 ├─ 5. DC 自助发布到共享开发调试环境并实测              │
 ├─ 6. 提交提测单 ──────────────────────────────────▶│ 7. 受理与代码 review
 │                                                     │ 8. 管理面/球端/接口复核
 │                                                     │ 9. 生产发布与观察窗
 │◀────────────── 10. 验收归档/问题回修 ───────────────┤
```

- 团队测试底座隔离：自助 publish **只进**测试底座（`tools/publish.sh` 拒绝一切 prod 参数），
  生产清单由平台方发布通道独占。
- 规模化后再议团队 scoped token；本期靠「提测制 + ownerTeam 登记 + 流程约定」。

## 8.3 发布前自检

团队侧按仓根 `RELEASE_CHECKLIST.md` 逐项勾选；平台方按 `PLUGIN_ACCEPTANCE.md` 逐项验收，
任一项不通过即退回补件。

带公开后端的包先执行 `node tools/check-api-contract.mjs extensions/<track>/<tier>/<pkg>`：
前端/管理页 `src/api/index.ts` 与后端公开 Spring Mapping 全路径双向对账，业务文件散落本包
服务 URL 也会报错。`publish.mjs --check-only` 与正式发布均自动执行该闸口，失败时不触网、不发布。

## 8.4 测试底座自助发布（publish.mjs + 双 shim）

团队自测通过后、提交提测单之前，可自助发布到测试底座联调（账号与地址见 `test-env/README.md`）：

```bash
# macOS / Ubuntu：构建 → DC release-prepare → upload-sessions+MinIO 直传+complete → release-complete
AGRSEARTH_TOKEN=... ./tools/publish.sh extensions/<track>/<tier>/<pkg>

# Windows CMD / PowerShell（同一 Node 实现）
# tools\publish.cmd extensions/<track>/<tier>/<pkg>

# HMR：终端 A 跑 npm run dev（watch）；终端 B 跑 npx vite preview --outDir dist --host 0.0.0.0 --port <端口>
# manifest 必须指向实际文件，不是 preview 根路径；有随包 CSS 时同时传 --dev-css-url
./tools/publish.sh extensions/<track>/<tier>/<pkg> --dev-url http://<本机IP>:<port>/tool.es.js \
  --dev-css-url http://<本机IP>:<port>/tool.css
# 无随包 CSS 时省略 --dev-css-url；reset 同时恢复 ESM 与已有 CSS 正式入口
./tools/publish.sh extensions/<track>/<tier>/<pkg> --dev-url --reset
```

约束（违反即拒）：

- **只打测试环境**；prod/生产参数一律拒绝（生产发布由平台管理员执行）；
- 发布控制 API **只走 developer-center**（`AGRSEARTH_TOKEN` 认证）——禁止直连
  resource-manager、禁止客户端自签 MinIO SigV4，亦不需要 MinIO 账号/密钥；
- 发布协议与产物处理由 Node 完成，不依赖 bash/jq/curl/python；npm 构建和可选
  `kubectl kustomize` 仍属项目构建工具链；
- 本机网络隔离时使用 `AGRSEARTH_SOCKS_PROXY=socks5h://127.0.0.1:51080`，DC、MinIO 和冒烟同走 SOCKS5；
- 首次发布前需有团队归属和包权限；交互开发用 dev-mcp 原生登录并自动复用令牌，CLI/CI 才显式配置 `AGRSEARTH_TOKEN`；
- **菜单号段零申请**：`components.menu.enabled=true` 的包经 dev-mcp `package_register`
  （resources.menu=true）后，DC 自动从本团队 band 池切出本包专属千段（团队池默认 10 块×10000 号/band，
  正常团队用不完）；`task_get` 跟踪发放任务到 ACTIVE、`resource_list` 实查本包段 [start-end] 后，
  把 `data/menu.json` 全部 menuId（含 parentId）改成段内值再发布。越段 fail-fast「禁止越段写菜单」
  报错自带本包实分段——改 menu.json 重发即可，**不要 quota_request**。注册一次性定资源位：
  menu=false 注册的包没有自己的段（重注册 409），需要菜单的包注册时就必须 menu=true，误注册走
  「`package_manage` remove → 重新注册」；仅团队池真用尽才
  `team_manage quota_request`，审批权在平台管理员（18850 开发者中心→任务页），TEAM_OWNER 不能自审，
  PENDING 期间不要重发版本；
- 带数据库的后端无需手填 Secret 名：DC deploy 自动把 `DB_URL/DB_USERNAME/DB_PASSWORD/DB_SCHEMA`
  收敛到本包 runtime Secret；`data/sql/*.sql` 随 release-complete 按 SHA-256 幂等应用，回执含 applied/skipped。
  预检提前校验文件名、非空、大小和 UTF-8 原文摘要；若校验失败，服务端错误会同时返回两端摘要与实际字符/字节数。

## 8.5 启用/停用与回滚

- **启用/停用（2026-10-18 B+ 定版）**：管理面「工具扩展」页对包的三动作——启用=按默认版本拉起（首启=bundle 安装，已停用=拉回，纯前端=宿主加载）；停用=整包组件停止（scale 0，**数据/卷/注册用户全保留**）；升级=平台方设默认版本后启用生效。包有平台强依赖组件时可声明 `manifest.json` 的 `lifecycle.stoppable: false` 禁停（sso 类基础组件平台内置禁停）。
- **回滚**：平台方执行——对上一已发布版本重新「启用」（资源中心保留全部历史版本）；
- 团队配合：提供回滚验证点（上一个稳定版的关键行为清单）；
- 数据迁移类变更必须提供**反向 SQL/降级脚本**或在提测单声明不可回滚点。

## 8.6 本地 Nacos 联调与人工确认后部署

后端开发遵循 **本地实现与接口验证 → 需要时接共享 Nacos 联调 → 人工确认 → 批准后部署**。前端另有 HMR 回路，见 §8.4。

### A. 本地直接验证（先做）

```bash
cd extensions/<track>/<tier>/<pkg>/backend/<svc>
mvn clean package
mvn spring-boot:run
# 另开终端；端口与健康路径以本包 bootstrap.yml / manifest 为准
curl http://localhost:<port>/info
curl http://localhost:<port>/<svc>/actuator/health
```

先用本地接口、单元测试和前端 HMR 验证业务逻辑。能直接在本机回答的问题，不必先操作共享环境。

### B. 接共享 Nacos 联调（需要全链时）

骨架 `bootstrap.yml` 的 Nacos discovery/config 默认指向 aiearth01 共享开发调试环境
（`10.82.11.51:18810`，可用 `SPRING_CLOUD_NACOS_DISCOVERY_SERVER_ADDR` /
`SPRING_CLOUD_NACOS_CONFIG_SERVER_ADDR` 覆盖）；配置 import 为 `optional:`，缺少业务 dataId 也能启动。

本地 `mvn spring-boot:run` 会把本机实例注册进共享 Nacos，但必须理解：

- **注册不会创建网关路由**。DC 仅在 `release-complete` 且 `deploy=true` 时，根据后端资源写入
  `Path=<apiPrefix>/** + StripPrefix=1 + lb://<serviceId>` 动态路由。
- **路由不会固定指向本机**。已有路由时，网关按服务发现在所有健康实例间负载均衡；本机与平台实例同时在线时，请求可能到任一端。
- 首次全新服务在尚未部署、没有既有路由时，不能宣称“注册 Nacos 后网关即可联调”。先完成本地直接验证，经人工确认和批准后进行首次受控部署，建立平台基线与路由；后续再利用本地实例联调。
- 全链联调要求双向可达：本机能访问 Nacos，平台网关也能访问本机 IP/端口。只能注册但请求超时时，优先检查平台到本机的回连，不要改共享配置。
- 注册共享 Nacos 会影响共享服务发现。AI 启动本地服务前应说明该副作用；结束联调及时停止本机服务并确认注销，不长期占用共享实例。

需要确定性地验证本机代码时，直接调用本机端口；不要把共享网关的一次成功响应当作一定命中本机。

### C. 人工确认后才部署

`publish` 与 `deploy` 不是同一件事：

- `deploy=false`：发布包版本与产物，不创建/更新工作负载、不写动态网关路由；但 release-complete 仍会执行菜单和已声明 `data/sql` 等发布动作，不能当作无副作用。
- `deploy=true`：追加镜像预检、动态路由注册和平台工作负载部署。AI 必须先给出本地/联调证据，由用户明确批准本次部署，不得默认追加。

首次部署后还要验证镜像形态、探针、resources、TZ、集群内寻址和真实接口；本地 jar 成功不能替代这些验收。给他人长期使用时应运行平台实例，不能依赖个人笔记本一直在线。
