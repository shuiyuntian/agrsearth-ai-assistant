# L0 AI 辅助开发：从业务想法到能力包

> 版本：1.0.0 ｜ 更新日期：2026-11-10 ｜ 维护口径：模板仓 AI 主入口；Agent 工作流、MCP 工具或审批边界变化时同步

本篇回答三个问题：**怎么接入 AI、怎样描述业务需求、哪些事情必须由人确认**。不需要先读完 L1-L10；完成首个最小能力包后，再按任务查阅后续篇章。

## 0.1 先明确分工

AI 可以读取仓库、提出方案、生成代码、运行检查、诊断日志，并在你批准后调用注册和发布工具。你需要提供业务目标，决定方案，批准有副作用的操作，并完成最终业务验收。

- AI 不应猜测数据来源、权限边界和验收标准；信息不足时应先追问。
- 构建通过只证明可构建，不等于球端、管理面和后端业务链路已经验证。
- 测试环境发布由团队经 developer-center 自助执行；生产发布始终由平台管理员执行。
- 不得让 AI 通过 SSH、直查数据库或修改共享配置绕过 developer-center。

## 0.2 首次接入

### 准备账号和工具链

先按 [L2 接入准备](./L2-接入准备-SSO与开发环境.md) 获得 SSO 开发者账号、团队归属和开发环境入口。开发机至少安装 Node.js 与 Git；只有带后端的包才需要 Java 17、Maven 和 Docker。

### 安装与自检

在模板仓根目录执行：

```bash
npm install
npm --prefix tools/dev-mcp install
node tools/agent-doctor.mjs --client kimi   # 按实际客户端替换为 codex/claude/qoder/opencode/trae/codebuddy
npm run check
```

然后用对应 AI 工具**以模板仓根目录为工作区**打开仓库，信任或批准项目级 MCP 配置。`agent-doctor` 必须显示 MCP、Skill、依赖全部通过；任一 FAIL 先按输出修复，不要直接开始开发。

### 检查登录

让 AI 调用 dev-mcp `auth_status`：

- 已登录且身份正确：继续。
- 未登录：调用 `auth_login_start`，由你在浏览器完成统一身份登录，再让 AI 调用 `auth_login_wait`。
- 无团队或包权限：联系团队负责人或平台管理员，不让 AI 尝试绕过权限。

交互开发不需要手工复制 token；`AGRSEARTH_TOKEN` 主要用于 CI 或命令行发布。

## 0.3 第一段提示词

复制以下内容到 AI 会话，替换方括号中的业务信息：

```text
请先阅读本仓 AGENTS.md，并使用 agrsearth-plugin-dev Skill 和 agrsearth-dev MCP。
先检查 agent-doctor 与 auth_status；如果接入或登录有问题，先告诉我怎么处理。

我要开发一个业务插件：
- 业务目标：[要解决的问题]
- 目标用户：[谁使用]
- 使用界面：[球端面板 / 管理页 / 都需要 / 请根据需求建议]
- 数据来源：[本地文件 / 第三方 API / 数据库 / 暂无]
- 地图交互：[需要展示什么、点击或绘制什么]
- 菜单与权限：[是否需要管理菜单、哪些操作需要授权]
- 验收标准：[看到什么、能完成什么操作]

请先读取必要的文档和示例，向我追问缺失的关键信息，然后给出：
1. track/tier/delivery 建议；
2. frontend/admin-ui/backend/data/menu 槽位取舍；
3. 实现步骤与验收清单；
4. 需要我批准的写操作。

本轮先只做调研和方案。未经我明确确认，不要建包、注册、发布或修改任何远程环境。
```

如果你还说不清需求，可以先说：**“我想做[业务目标]，请通过提问帮我补齐一份可实现、可验收的需求说明。”**

## 0.4 标准协作流程

| 阶段 | AI 应交付 | 你需要做什么 |
|:---|:---|:---|
| 1. 接入检查 | doctor、登录和权限状态 | 修复本机依赖，完成浏览器登录 |
| 2. 需求澄清 | 业务理解、缺失问题、非目标 | 回答业务问题，提供样例数据或设计图 |
| 3. 方案 | 分类、槽位、文件范围、验收标准 | 明确回复“按此方案建包/实施” |
| 4. 本地实现 | 脚手架产物、业务代码、README/CHANGELOG | 审查关键业务行为，不要求逐行监督 |
| 5. 本地验证与联调 | 构建、URL 对账、本地接口结果；需要全链时说明 Nacos 注册、路由和双向可达状态 | 审查本地证据并确认是否具备部署条件 |
| 6. 注册与资源发放 | 团队、包 ID、menu/postgres 开关、任务状态 | 明确批准注册；等待任务 ACTIVE |
| 7. 测试发布/部署 | 包目录、版本、deploy 选择和发布事由 | 明确批准本次发布；后端 `deploy=true` 需另行确认 |
| 8. 验收与交付 | 实测证据、未验证项、已知问题、提测材料 | 在真实页面确认业务结果，决定是否提测 |

**后端先本地直接验证，需要全链联调时才注册到共享 Nacos。Nacos 注册不自动创建网关路由，也不保证请求只到本机。人工确认本地/联调结果后，AI 才可请求批准后端的 `deploy=true`。** 详见 L8 §8.6。纯前端没有后端工作负载部署，但首次远程加载仍需先发布产物。

**注册、发布、资源签发不是“顺手执行”的默认步骤。** AI 每次都应说明对象、环境和影响，得到你本次明确批准后再执行。包移除、转移等高风险操作必须单独确认。

## 0.5 完整对话示例

以下是对话结构示例，实际工具结果以你的环境为准。

**用户：**

> 我要做一个“重点河道水位”插件，在球端面板显示 5 个演示站点，地图上有标记，点击标记能看到当前水位。先用本地 JSON，不要后端和管理页。请先给方案，不要建包。

**AI 应做的回应：**

> 建议 `tool/business/optional`，只启用 `frontend`，不启用 backend/admin-ui/menu/data。面板提供站点列表和状态，地图标记通过 `ctx.entities` 分组管理；点击后展示水位详情。验收包括列表与地图一致、点击可查看、反复启停无重复实体。确认后我再建包。

**用户：**

> 按这个方案实施，包 ID 用 `river-watch`，名称用“重点河道水位”。只做本地开发和预检。

**AI 应完成：**

> 使用 `package_scaffold` 建包，编写面板与地图交互，更新包 README/CHANGELOG，运行构建、`package_precheck` 和红线检查，最后列出修改文件与检查结果。此阶段不注册、不发布。

**用户：**

> 本地结果我认可。请检查登录和团队，告诉我注册将创建哪些资源位。

**AI 应完成：**

> 通过 `auth_status`、`team_list` 确认身份和团队，说明本次注册只需包归属，不使用 PostgreSQL/菜单资源位，然后等待批准。

**用户：**

> 批准注册到当前团队。

**AI 应完成：**

> 调用 `package_register`，再用 `task_get` 跟踪到 ACTIVE；失败时报告真实状态，不把“已受理”说成“已完成”。

**用户：**

> 批准将 `river-watch` 当前版本发布到共享开发调试环境，不部署后端。

**AI 应完成：**

> 再次预检后调用 `package_publish`，报告发布版本与冒烟结果；随后提供或执行真实球端验收。没有浏览器能力时，明确列出人工验证步骤，不声称页面已经通过。

## 0.6 常用提示词

### 修改现有插件

```text
请修改 extensions/<track>/<tier>/<pkg> 的 <具体功能>。
先阅读该包 README、相关源码和适用 Recipe，说明修改范围与验收方式后再动手。
保持现有公共契约不变；完成后运行相关构建和预检，列出实际结果与未验证项。
不要注册或发布，等我确认。
```

### 排查构建或运行问题

```text
请排查 <包/页面> 的 <错误原文或现象>。
先读取实际错误、相关源码和 docs/L9-FAQ与排错.md，复现并定位根因后再修改。
不要通过跳过校验、关闭鉴权或直连服务器来绕过问题。
修复后重跑同一检查，并给出前后结果。
```

### 发布前审查

```text
请只读审查 extensions/<track>/<tier>/<pkg> 当前改动：
对照业务需求、AGENTS.md、RELEASE_CHECKLIST.md 和适用 Recipe，
检查构建、版本、菜单、权限、URL 契约与资源清理。
输出通过项、阻塞项和未验证项；不要修改代码，不要发布。
```

## 0.7 国际资源访问失败时

国内开发机访问国际包仓库、镜像源或文档站点失败时，先保留原始错误并判断是否为网络问题。开发团队默认使用 Clash，但 AI 应**优先只读检查并复用本机已有代理**，不假定固定端口，不擅自启停 Clash 或修改系统代理。

代理只用于当前国际资源请求，内网与环回地址保持直连；它与访问开发底座的 `AGRSEARTH_SOCKS_PROXY` 隧道是两种不同通道。详细规则见 [L9 开发机环境排错](./L9-FAQ与排错.md)。

## 0.8 怎样才算完成

让 AI 在结束时提供：

- 需求与实现对照，包含明确不做的事项；
- 修改文件和包版本；
- 实际执行的构建、测试、预检命令及结果；
- 注册任务、发布版本和远程状态（只有实际执行后才写）；
- 球端/管理面/后端的真实验证证据；
- 未验证项、已知问题、风险与下一步。

如果只有本地验证，结论应写“本地构建与预检通过，远程和业务页面待验证”，而不是“插件已完整交付”。
